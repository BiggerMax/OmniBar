## 0. TL;DR

- **两个开关**（Claude Code、Codex）→ **四个目标**（Claude Code CLI、Claude Desktop、Codex CLI、ChatGPT Desktop）。
- 借鉴 cc-switch 的安全层（原子写、快照回滚、备份、接管检测），但不照搬它的「多供应商 DB + 整体换文件」模型 —— omniroute 已是单端口多协议聚合网关，OmniBar 只需把网关配置"焊接"进各工具 live 文件。
- 已有一版骨架代码（ProviderLinkManager / 三个 LiveConfig 写器 / ModelCatalog / 设置页 UI），见第 7 节现状盘点；**测试 target 引用了不存在的测试文件，需在 M1 补齐**。
- 最大不确定点是 Claude Desktop 模型枚举（见 9.2），需要 spike 后才能定稿。

## 1. 背景与目标

OmniBar 目前只做「监控 + 启停 omniroute 网关」。用户日常在 Claude Code CLI、Claude Desktop（Claude Code desktop）、Codex CLI、ChatGPT Desktop 中编码时，需要能使用 omniroute 里已经配好的服务商（各 Provider + Combo 路由）。目前这项工作靠手工改配置文件，或用 cc-switch 这类第三方桌面工具。

**v2.0 目标**：在 OmniBar 内提供 **Claude Code** 与 **Codex** 两个主开关；开启后把 omniroute 网关"焊接"进各工具的 live 配置，使四个目标应用都能**选择 omniroute 服务商**：

| 开关 | 目标应用 | 接入方式 | 用户如何选择 omniroute 服务商 |
|---|---|---|---|
| Claude Code | Claude Code CLI | 写 `~/.claude/settings.json` 的 `env` 块 | `/model` 原生菜单枚举网关模型 + OmniBar 设置的默认模型 |
| Claude Code | Claude Desktop（Claude Code desktop） | 写 3P 部署 profile（`~/Library/Application Support/Claude/`） | Claude Desktop 模型菜单（需 spike 确认，见 9.2） |
| Codex | Codex CLI | 写 `~/.codex/auth.json` + `config.toml` + 模型目录 | `/model` 经生成的 `omnibar-model-catalog.json` 枚举网关模型 |
| Codex | ChatGPT Desktop | 内嵌 Codex，读同一份 `~/.codex/` | 同 Codex CLI；重启桌面端生效 |

**验收定义**：任一开关开启后，对应目标应用内能稳定路由到 omniroute 网关（`http://localhost:{port}/v1`），模型列表来自网关 `/v1/models`，且不破坏用户原有配置（hooks / MCP / 其它 provider / 其它管理器）。

## 2. 调研报告

### 2.1 cc-switch 工作机制（核心调研对象）

**仓库与形态**：`farion1231/cc-switch`（Tauri 2 + Rust + React + SQLite），CLI 社区分支 `SaladDay/cc-switch-cli`。支持 8 个工具：Claude Code CLI、Claude Desktop、Codex CLI/App、ChatGPT Desktop、Gemini CLI、OpenCode、OpenClaw、Hermes Agent。

**核心数据模型（SSOT）**：
- `~/.cc-switch/cc-switch.db`（SQLite）：`providers` 表，每行 = 一个供应商配置；`settings_config` 字段存**按应用格式**的配置 JSON；`is_current` 标记当前激活；`meta` 存内部字段。
- `~/.cc-switch/settings.json`：设备级偏好。

**工作机制**：
1. **Exclusive 模式**（Claude / Claude Desktop / Codex / Gemini）：每应用同时只激活一个供应商。切换 = 把 `settings_config` **整体写回**目标 live 文件。
2. **Backfill（回填）**：切换前把当前 live 文件内容读回 DB，保护用户在 UI 之外的手工修改。
3. **Sanitize（清洗）**：写入前 `sanitize_claude_settings_for_live` 剥离内部字段，只留工具认识的最小集。
4. **写 Claude Code**：`~/.claude/settings.json` 整体替换，`env` 块含 `ANTHROPIC_BASE_URL` / `ANTHROPIC_AUTH_TOKEN` / `ANTHROPIC_MODEL` / `ANTHROPIC_DEFAULT_{SONNET,OPUS,HAIKU,FABLE}_MODEL` / `CLAUDE_CODE_SUBAGENT_MODEL`。提供 `skipDangerousModePermissionPrompt` 跳过 Claude Code 首次登录引导。
5. **写 Codex**：`~/.codex/auth.json`（`OPENAI_API_KEY`）+ `~/.codex/config.toml`（`model_provider="custom"`、`model=...`、`model_catalog_json="cc-switch-model-catalog.json"`、`[model_providers.custom]` 含 `name`/`wire_api="responses"`/`requires_openai_auth=true`/`base_url`）+ 生成模型目录 `cc-switch-model-catalog.json`（以 gpt-5.x 为模板克隆出第三方模型，供 `/model` 列出）。**auth 写成功而 toml 写失败时回滚 auth**。
6. **写 Claude Desktop**：3P 部署模式（详见 2.4）。
7. **ChatGPT Desktop / Codex.app**：内嵌的 Codex CLI 读同一 `~/.codex/` 目录 → 写 Codex 即覆盖。
8. **安全机制**：`atomic_write`（tmp 文件 + rename）、快照回滚、自动备份（`~/.cc-switch/backups/`，保留 10 份）、backfill。

**本机实证**：cc-switch 已存 `omniroute` / `Tokenrouter` / 官方等供应商；当前激活的 `omniroute` 供应商的 Claude 配置即 `ANTHROPIC_BASE_URL=http://localhost:20128/v1`、`ANTHROPIC_MODEL=PY/deepseek-v4-flash-0731[1M]`；Codex 配置即 `model_provider="custom"` + `base_url=http://localhost:20128/v1`。**这些正是 v2.0 要自动生成的内容。**

### 2.2 Claude Code 配置机制

- **连接网关的三个入口**：`ANTHROPIC_BASE_URL`（覆盖 `https://api.anthropic.com`）、`ANTHROPIC_AUTH_TOKEN`（`Authorization: Bearer <token>`）、`ANTHROPIC_API_KEY`（`x-api-key: <key>`）。设置任一即绕过 claude.ai 订阅登录，按网关 Token 计费。
- **settings.json 的 `env` 块**：把上述变量固化到 `~/.claude/settings.json` 的 `env` 字段，Claude Code 启动时自动注入，无需 shell export。
- **配置文件优先级（高 → 低）**：企业/托管策略 > 项目本地 `.claude/settings.local.json` > 项目级 `.claude/settings.json` > 用户级 `~/.claude/settings.json`；shell 环境变量优先级最高。
- **默认模型键**：`ANTHROPIC_MODEL` 是会话默认；`ANTHROPIC_DEFAULT_SONNET_MODEL` / `_OPUS_MODEL` / `_HAIKU_MODEL` / `_FABLE_MODEL` / `CLAUDE_CODE_SUBAGENT_MODEL` 控制各角色/子代理的模型映射 —— 网关模型 id 无 `claude-*` 语义时，把四个角色键都指到同一网关模型是 cc-switch 的通行做法。
- **验证**：会话内 `/status` 显示当前 base URL；`/model` 可切换。

### 2.3 Codex CLI / ChatGPT Desktop 配置机制

- **路径**：`CODEX_HOME`（默认 `~/.codex/`）下 `config.toml`（TOML）+ `auth.json`。ChatGPT Desktop 与 Codex CLI **共享同一份 `~/.codex/config.toml`**（桌面端也可通过 Settings > Configuration > Open config.toml 编辑），写 Codex 即覆盖两者。
- **自定义网关**：不能覆盖内置 `openai` provider，必须自定义 `[model_providers.<id>]`：
  - `name`：显示名（必填）
  - `base_url`：网关 API 基础路径（通常以 `/v1` 结尾）
  - `wire_api`：**新版 Codex 已废弃并移除 `"chat"`，必须用 `"responses"`**（对应 OpenAI Responses API）
  - `env_key`：指向环境变量名（`"OPENAI_API_KEY"` 等），运行时从环境读取 Key
  - `requires_openai_auth`：`true` 走 OpenAI 认证体系（配合 auth.json 的 API Key）；`false` 跳过"Sign in with ChatGPT"登录拦截
  - `http_headers` / `env_http_headers`：可选注入自定义请求头
- **凭证存储**：`~/.codex/auth.json`（明文，含 `OPENAI_API_KEY`）或系统 keyring（`cli_auth_credentials_store = "keyring"`）。
- **模型选择**：顶层 `model = "..."` 默认模型、`model_provider = "custom"` 默认供应商；`model_catalog_json` 指向外部模型目录文件（`/model` 菜单据此枚举）；支持 `codex --profile <name>` 加载 `~/.codex/<name>.config.toml`。
- **cc-switch 的取舍**：写 `auth.json` 的 `OPENAI_API_KEY` + `requires_openai_auth=true`（走 API Key 认证而非 OAuth 长 Token），实测稳定。

### 2.4 Claude Desktop（Claude Code desktop）3P 配置机制

- **开发者模式**：Claude Desktop 支持 Help > Troubleshooting > Enable Developer Mode 后，通过 Developer > Configure Third-Party Inference 手动配网关；企业可用 MDM 托管配置推送。
- **3P 部署文件结构**（cc-switch 采用同一路径，本机实证）：
  - `~/Library/Application Support/Claude/claude_desktop_config.json` → `{"deploymentMode":"3p"}`
  - `~/Library/Application Support/Claude-3p/claude_desktop_config.json` → `{"deploymentMode":"3p"}`
  - `~/Library/Application Support/Claude-3p/configLibrary/<uuid>.json`：profile，含 `inferenceGatewayBaseUrl`、`inferenceGatewayApiKey`、`inferenceGatewayAuthScheme:"bearer"`、`inferenceProvider:"gateway"`、`inferenceModels:[...]`、`coworkEgressAllowedHosts`、`disableDeploymentModeChooser`
  - `~/Library/Application Support/Claude-3p/configLibrary/_meta.json`：记 `appliedId` / `entries`（激活哪个 profile）
- **关键约束**：直连模式下 `inferenceModels` 必须是 **`claude-*` 角色名**（如 `claude-sonnet-4-5`），否则 Claude Desktop 的 fail-all validator 拒收整组配置；非 claude 模型必须走"本地路由代理"模式（本地端口把 `claude-*` 请求映射改写 model 后转发网关）。
- **恢复官方**：deploymentMode 改回 `1p`，删除 profile 与 appliedId 记录。

### 2.5 omniroute 网关能力（本机实测）

omniroute 是**单端口多协议**本地网关（默认 20128），统一用 omniroute API Key 做 Bearer 鉴权：

| 面 | 端点 | 实测结果 |
|---|---|---|
| OpenAI Chat | `POST /v1/chat/completions` | ✅ `model=auto/best-fast` 正常流式返回 |
| OpenAI Responses | `POST /v1/responses` | ✅ 正常返回（Codex 兼容） |
| Anthropic Messages | `POST /v1/messages` | ✅ `model=pro` 正常返回（路由到 `moonshotai/kimi-k3-free`） |
| 模型列表 | `GET /v1/models` | ✅ 返回 `auto/best-*`、`PY/...`、`Sense/...` 等全部模型与 `context_length` |
| 管理 API | `/api/providers` `/api/combos` 等 | ✅ 已接入（OmniBar 现有） |

要点：
- **一个 key 一个端口同时满足 Claude（anthropic 协议）、Codex（responses 协议）、OpenAI（chat 协议）**，这是 v2.0 能轻量实现的前提。
- Provider 的 `providerSpecificData.prefix`（如 `PY`/`Sense`/`UN`）构成模型 id 前缀 `prefix/model`；Combo 提供 `auto/best-*` 虚拟模型。
- `model=claude-sonnet-*` 这类名字**当前不被网关路由**（实测上游 401）—— 影响 Claude Desktop 接入，见 9.2。

### 2.6 关键洞察与借鉴点

| 借鉴 cc-switch | 不照搬 cc-switch |
|---|---|
| 原子写（tmp + rename） | 多供应商 SQLite DB（OmniBar 只需一个 omniroute） |
| 快照回滚 / 自动备份 | 整体替换 live 文件（改用 merge / 哨兵块，降低误伤） |
| 接管标记 / 冲突检测 | 本地代理守护进程（仅 Claude Desktop 兜底时引入） |
| backfill（保护用户手工修改） | 多应用 CLI 管理面（cc-switch-cli） |

本机已用 cc-switch 管理 claude/codex 配置，OmniBar 与 cc-switch 是**竞争关系**，需做好接管检测与共存提示（见 6.6）。

## 3. 需求规格

### 3.1 用户故事

- 作为 Claude Code CLI 用户，我在 OmniBar 打开「Claude Code」开关后，`claude` 会话内 `/model` 能列出 omniroute 网关的全部模型，且默认模型即我在 OmniBar 里选的模型；关闭开关后配置完全还原。
- 作为 Claude Desktop 用户，我打开同一开关后，桌面端模型菜单能选到 omniroute 服务商（按 9.2 决策的方案实现）。
- 作为 Codex CLI 用户，我打开「Codex」开关后，`codex` 会话内 `/model` 能列出网关模型，默认走网关；关闭后还原。
- 作为 ChatGPT Desktop 用户，我打开「Codex」开关并重启桌面端后，内置 Codex 同样走网关。
- 作为已用 cc-switch 的用户，OmniBar 接管前会提示冲突并备份，误接管后能一键恢复。

### 3.2 功能需求

| 编号 | 需求 | 验收 |
|---|---|---|
| FR1 | 设置页新增「AI 接入」Tab，含 Claude Code、Codex 两个开关 | 开关状态 `@AppStorage` 持久化，重启不丢 |
| FR2 | 开启 Claude Code 开关 → 写 `~/.claude/settings.json` env 块 | 新 claude 会话 `/status` 显示网关 base URL，`/model` 可选网关模型并能出结果 |
| FR3 | 开启 Codex 开关 → 写 auth.json + config.toml + 模型目录 | `codex` 会话 `/model` 含网关模型并能出结果；ChatGPT Desktop 重启后同样生效 |
| FR4 | 每目标可选默认模型（默认取网关第一个模型 / 当前 active Combo） | 模型选择持久化并写入对应配置 |
| FR5 | 关闭任一开关 → 精确剥离托管内容并回滚备份 | 相关文件恢复字节级原样（或删除原不存在的文件） |
| FR6 | 端口 / API Key / 模型变化 → 已开启目标自动重写 | 各 live 文件始终指向当前网关 |
| FR7 | 接管前冲突检测（cc-switch 等） | 弹提示 + 自动备份 + 用户确认 |
| FR8 | 接管后外部改写检测 | 状态提示「配置被外部工具修改」+ 一键恢复 |
| FR9 | 全程不破坏用户原有配置 | hooks / MCP / 其它 provider / 其它管理器内容保留 |
| FR10 | 模型目录为自用文件名 `omnibar-model-catalog.json` | 不与 cc-switch 的 catalog 冲突 |
| FR11 | Claude Desktop 接入 | 按 9.2 决策验收 |

### 3.3 非功能需求

- **原子性**：任何写盘失败不留半截文件（tmp + rename）。
- **可恢复性**：关闭/还原按钮可恢复接入前状态；备份保留在 `~/Library/Application Support/OmniBar/backups/`。
- **幂等**：enable / disable / 重写跑多遍结果一致。
- **响应性**：模型目录模板获取等阻塞操作限时（8s）且不卡 UI。

## 4. 设计决策

| # | 决策 | 说明 |
|---|---|---|
| D1 | **两个主开关**（Claude Code、Codex），`@AppStorage` 持久化 | 语义清晰；Claude Desktop 并入 Claude Code 开关、ChatGPT Desktop 并入 Codex 开关（共用配置面） |
| D2 | **merge 而非整体替换**（Claude） | 只 merge `env` 键，不动用户 hooks/MCP/其它设置，降低误伤面（优于 cc-switch 的整体替换） |
| D3 | **哨兵标记块 + 幂等**（Codex） | `config.toml` 用 `# >>> omnibar-managed >>>` 注释块包裹托管键；enable/disable/更新幂等，保留用户其余配置 |
| D4 | **备份 + 回滚** | 开启前备份原文件；关闭时恢复；提供手动恢复入口 |
| D5 | **模型选择器按目标** | 每目标可选默认模型（默认 = 网关首个模型 / 当前 active Combo），写入 `ANTHROPIC_MODEL` / `model=`；同时允许工具内原生选择 |
| D6 | **自用模型目录文件名** | `omnibar-model-catalog.json`，避免与 cc-switch 冲突 |
| D7 | **端口 / Key / 模型联动重写** | 设置变化时对已开启目标幂等重写，保证始终指向当前网关 |
| D8 | **Claude Desktop 直连优先，映射代理兜底** | 先 spike 验证直连能否枚举模型（方案 A）；失败再上本地映射代理（方案 B），见 9.2 |
| D9 | **Codex 协议固定 `wire_api="responses"`** | 新版 Codex 已移除 chat 协议；用 auth.json + `requires_openai_auth=true`（对齐 cc-switch 实测配置） |
| D10 | **接管检测分级处理** | 检测到他人托管 → 提示 + 备份 + 确认；接管后被外部改写 → 提示 + 一键恢复 |

## 5. 架构设计

```
AppDelegate
  └─ ProviderLinkManager (@MainActor ObservableObject)
       ├─ 状态: claudeEnabled / codexEnabled / lastResult / isBusy
       ├─ 入口: enable(.claudeCode) / disable(.claudeCode) / enable(.codex) / disable(.codex)
       │         toggle(target, gatewayModels:)     // UI 开关用
       │         refreshAll()                       // 网关状态/模型/端口/key 变化时幂等重写
       │         restoreBackup(target)
       ├─ 目标 live 写器（每个目标一个文件，纯函数化、可单测）
       │    ├─ ClaudeCodeLiveConfig    → merge env 到 ~/.claude/settings.json
       │    ├─ CodexLiveConfig         → auth.json + config.toml(哨兵块)
       │    └─ ClaudeDesktopLiveConfig → 3P profile + _meta.json + deploymentMode（M4）
       ├─ ModelCatalogBuilder          → GET /v1/models → omnibar-model-catalog.json
       └─ AtomicWriter                 → tmp + rename + 备份/回滚（BackupManager）
      输入
       ├─ AppSettings（端口/Key/开关/每目标模型选择）
       └─ OmnirouteService（gatewayModels、activeCombo 模型）
```

**数据流**：
1. 用户拨开关 → `AIIntegrationSettings.toggleLink` → `manager.toggle(target, gatewayModels:)` → 写器 → 结果消息回显。
2. 端口 / Key / 模型变化 → `AppSettings.objectWillChange` → `ProviderLinkManager.scheduleRefreshIfLinked`（400ms 防抖）→ 对已开启目标重写。
3. 启动时 → AppDelegate 对已开启开关幂等 apply（`refreshAll`）。
4. 模型列表 → `OmnirouteService.refresh()` 拉 `GET /v1/models` 存 `gatewayModels`。

## 6. 详细设计

### 6.1 Claude Code CLI 写器（ClaudeCodeLiveConfig）

目标：`~/.claude/settings.json` 的 `env` 键（merge）。

```
托管 env 键（关闭时精确移除这些键，保留用户其它 env / hooks / MCP）:
  ANTHROPIC_BASE_URL          = http://localhost:{port}/v1
  ANTHROPIC_AUTH_TOKEN        = {omnirouteAPIKey}
  ANTHROPIC_MODEL             = {claude 目标模型}
  ANTHROPIC_DEFAULT_SONNET_MODEL / _OPUS_MODEL / _HAIKU_MODEL / _FABLE_MODEL
  CLAUDE_CODE_SUBAGENT_MODEL
```

- **merge**：读现有 JSON（不存在则 `{}`），`env` 对象里 set 托管键，其余键原样保留，原子写回。
- **开启前备份**：`BackupManager.ensureBackup` 复制原文件。
- **关闭**：剥离托管键写回；若文件原本不存在则删除。
- **模型**：默认取网关首个模型 / active Combo 模型，或用户选定；`[1M]` 后缀透传（现有用法如此）。会话内 `/model` 可枚举网关模型，OmniBar 只负责默认值。
- **生效**：新会话生效（cc-switch 文档称支持热切换，实现时验证，不阻塞）。

### 6.2 Codex CLI / ChatGPT Desktop 写器（CodexLiveConfig）

目标：`~/.codex/auth.json` + `~/.codex/config.toml` + `~/.codex/omnibar-model-catalog.json`。

- **auth.json**：`{ "OPENAI_API_KEY": "{omnirouteAPIKey}" }`。
- **config.toml**（哨兵块，保留用户其余内容）：

```toml
# >>> omnibar-managed >>>
model_provider = "custom"
model = "auto/best-fast"
model_reasoning_effort = "high"
disable_response_storage = true
model_catalog_json = "omnibar-model-catalog.json"

[model_providers.custom]
name = "omniroute"
wire_api = "responses"
requires_openai_auth = true
base_url = "http://localhost:{port}/v1"
# <<< omnibar-managed <<<
```

### 6.4 模型目录生成（ModelCatalogBuilder）

- 输入：`GET /v1/models` 结果 + 模板条目；输出：`{"models":[...]}` JSON。
- 模板来源：`codex debug models --bundled`（限时 8s）→ `~/.codex/models_cache.json` → 内置静态模板（gpt-5.x 结构）。
- 每个网关模型生成条目：`slug`=模型 id、`display_name`/`description`=短名、`context_window`/`max_context_window`=网关 `context_length`、`priority` 递增；按 `capabilities` 推断 `supports_reasoning_summaries` / `supports_image_detail_original`。
- **NativeResponses profile**：`shell_type="shell_command"`，**不声明** freeform `apply_patch`/`web_search` 工具（镜像 cc-switch 的 `codex_native_responses_template`），避免网关拒收 custom 工具。
- 网关模型数通常几十个，全量生成；模板缺失时至少暴露当前选中模型。

### 6.5 备份 / 回滚（AtomicWriter + BackupManager）

- **原子写**：同目录 `.name.omnitmp` 临时文件 + rename，确保完整替换。
- **备份**：`~/Library/Application Support/OmniBar/backups/<marker>-<basename>`，如 `omnibar:claudeCode-settings.json`；仅首次真正复制（幂等）。
- **回滚**：关闭时以备份覆盖（原文件不存在则删除）；成功后清理备份。手动恢复入口同样复用。
- 标记：`LinkTarget.marker = "omnibar:<target>"`。

### 6.6 冲突检测与共存（cc-switch / 其它管理器）

- **接管前检测**：
  - Claude：`settings.json` 的 `env.ANTHROPIC_BASE_URL` 指向非本网关（如 `api.tokenrouter.com`、`127.0.0.1:15721`）→ 提示「当前由 cc-switch 托管，开启将覆盖；已自动备份」，确认后执行。
  - Codex：`config.toml` 含其它管理器哨兵（如 `cc-switch-model-catalog.json`、`experimental_bearer_token="PROXY_MANAGED"`、其它哨兵注释）→ 同理提示。
- **接管后检测**：OmniBar 已接管且检测到 live 文件被外部改写（托管键被改/删）→ 状态行提示「配置被外部工具修改」，提供一键恢复。
- **原则**：同一工具同一时刻只应被一个管理器接管；把「双管理器互踩」从数据损坏降级为「提示 + 可恢复」。

### 6.7 联动刷新

- 订阅 `AppSettings.objectWillChange`（异步分发，避免 SwiftUI 更新期断言崩溃），400ms 防抖。
- 已开启目标 → 重新 enable（幂等）。**注意**：刷新路径需拿到最新 `gatewayModels` 再重生成模型目录（现状实现传空数组，刷新时会退化为仅当前模型，见 7 的 G4）。

## 9. 风险与开放问题（审阅决策点）

### 9.1 【已拍板】Claude Desktop 模型枚举方案（M0 决策）

**决策（2026-08-04）**：采用**方案 A —— 先 spike 直连**。Phase 4 先做 A 的 spike（`curl` 验证网关 `/v1/models` 能否被 Claude Desktop 消费 + 桌面端手测）；失败则上方案 B 本地映射代理。

背景：omniroute 不路由 `claude-*` 模型名（实测 401），而 Claude Desktop 3P 直连模式的 `inferenceModels` 必须 `claude-*` 角色名。三条路径：

omniroute 不路由 `claude-*` 模型名（实测 401），而 Claude Desktop 3P 直连模式的 `inferenceModels` 必须 `claude-*` 角色名。三条路径：

- **A. 不写 `inferenceModels`，只写 baseUrl + key**：依赖 Claude Desktop 在 `inferenceProvider="gateway"` 时主动拉取网关 `/v1/models` 展示模型菜单。若 omniroute 的 `/v1/models`（OpenAI 风格）能被其消费 → 用户即可在 Claude Desktop 直接选 omniroute 服务商。**实现前 spike 验证**，成本最低。
- **B. 轻量本地映射代理**：OmniBar 内嵌本地端口代理，收到 `claude-*` 请求 → 按映射改写 `model` → 转发 omniroute（镜像 cc-switch 本地路由）。约 300–500 行，能真正满足「在 Claude Desktop 中选择 omniroute 服务商」。A 失败时的兜底。
- **C. 请求 omniroute 侧增加 claude-* 别名**：超出 OmniBar 范围，仅作为上游建议。

> **建议**：Phase 2 先做 A 的 spike（`curl` 验证 + 桌面端手测）；失败则上 B。

### 9.2 【已拍板】与 cc-switch 共存策略（M0 决策）

**决策（2026-08-04）**：**OmniBar 与 cc-switch 独立运行；OmniBar 实现 claude/codex 路由后，用户将不再使用 cc-switch**。因此 OmniBar 成为唯一接管者：接管前仍做冲突检测 + 自动备份 + 提示（6.6，成本低、防误伤），但**不实现双向接管协商**（cc-switch 侧改动检测仅做提示 + 一键恢复）。文档层面明确：同一工具同一时刻只应被一个管理器接管。

### 9.3 【待确认】Claude Code 热切换

cc-switch 文档称 Claude Code 支持不重启热切换；实测确认。若不支持，开启后提示「新会话生效」即可，非阻塞。

### 9.4 密钥处理

写入的是 omniroute 网关自己的 API Key（工具 → 本地网关的鉴权），与 cc-switch 行为一致；不涉及第三方密钥新增落盘面。Codex `auth.json` 明文存在于用户主目录（原生行为如此）。

### 9.5 `[1M]` 后缀与 1M 上下文

Claude 侧沿用现有 `[1M]` 后缀用法。Claude Desktop 不接受 `[1M]`（`supports1m` 字段替代），实现时翻译。

### 9.6 wire_api 版本漂移

新版 Codex 已移除 `wire_api="chat"`；若用户 Codex 版本过旧不支持 `"responses"`，需在 UI 提示升级（或按版本写不同协议）。
